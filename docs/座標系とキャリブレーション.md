# 座標系とキャリブレーション

計測系が3つ（カメラ・オドメトリ・メジャー実測）あり，それぞれ原点と軸の向きが違います．
突き合わせのたびに迷わないよう，定義と換算をここにまとめます．

---

## 1. カメラ計測の座標系

天井に固定したスマートフォンで真上から撮影し，機体上面の赤マーカーを追跡します．

- **原点**：画像の右上
- **x軸**：右上 → 左上方向（左に進むほど正）
- **z軸**：右上 → 右下方向（下に進むほど正）
- **単位**：mm

画像座標は左手系なので，オドメトリ（右手系）と比較するときは**yを反転**してから揃えます．

### スケールの決定

床に既知寸法の色付き正方形（参照マーカー）を置き，その一辺の見かけpx数から `mm/px` を自動算出します．
クリックによるキャリブレーションは不要です．

参照マーカーの検出は3段階で行います．

1. 緩い色閾値で候補領域を粗く見つける
2. 見つかった領域の実際の色に閾値を合わせ直す
3. 紙色と床色を結ぶ色軸への射影で，半値交差点からサブピクセル精度でエッジを求める

3段階目が必要な理由は，JPEG/クロマ圧縮でエッジが内側ににじみ，**一辺が約2%短く出る**ためです．

### カメラ高さの補正

マーカーは床面ではなく機体上面（床から `h`）にあり，カメラは床から `H` の高さにあります．
床基準のスケールをそのまま適用すると見かけの移動量が過大になるため，次の比を掛けます．

```
補正係数 = (H - h) / H
```

実測値の例：`H = 1990 mm`（カメラ高さ），`h = 161 mm`（マーカー高さ）

### 自己検証

マーカーの実径は42.5mmです．
検出した見かけ径を実径と比較して毎回表示させると，スケール決定から高さ補正までの一連の計算が
壊れていないかを1行で確認できます．

## 2. 赤マーカーの検出閾値

赤はHueが0°をまたぐため，両端の2レンジを合成したマスクを使います．

| レンジ | 下限 | 上限 |
| --- | --- | --- |
| 低Hue側 | `[0, 160, 80]` | `[10, 255, 255]` |
| 高Hue側 | `[165, 160, 80]` | `[180, 255, 255]` |

同じ赤紙でも，明るい場所ではH≈177，暗い場所ではH≈6と大きく振れます．
これはスマートフォン側のホワイトバランスが効いているためで，2レンジ併用はこの対策です．

一方，低Hue側は濃い木目や壁際を誤検出することがあります．
撮影環境が安定していて誤検出のほうが問題になる場合は，低Hue側を外す判断もあります．
`マスク確認.jpg` を見て，マーカーだけが白く抜けているか毎回確認してください．

### ノイズ対策

- モルフォロジー **OPEN → CLOSE**：暗所でマスクに空く穴を埋める
- **最大輪郭のみ採用** ＋ 最小面積フィルタ
- **ジャンプゲート**：1フレームで `MAX_JUMP_PX = 80` を超える移動は棄却．15フレーム連続で棄却が続いたら追従が外れたとみなしてリセット

### 参照マーカー（ティール色）の閾値

| 項目 | 値 |
| --- | --- |
| 下限 | `[40, 70, 40]` |
| 上限 | `[125, 255, 255]` |

見た目は緑ですが，実測ではH≈97のティールでした．
色名の思い込みで閾値を決めず，必ず実測してください．

## 3. オドメトリの座標系

Pybricksのログ（`pybricks-data-*.csv`，UTF-8 BOM付き）を使います．

| 列名 | 内容 | 単位 |
| --- | --- | --- |
| `odo_x` | x座標 | cm |
| `odo_y` | y座標 | cm |
| `o_deg` | 方位角 | 度 |

`o_deg` は**初期進行方向で0°，反時計回りが正**です．

### プロット時の変換

```python
plot_x = -odo_x          # 写真の向きに合わせて符号反転
plot_y =  odo_y          # そのまま
theta  = 90 + o_deg      # 描画用の方位角
```

`odo_x` の符号反転が要るのは，写真の向きで見たとき `odo_x` が左方向を正としているためです．

## 4. 車輪半径の較正

過去に距離が約3.5%足りない不具合がありました．原因は単純な定数の不一致です．

- `OdometryWithGyro` は `wheel_radius = 2.7 cm`
- エンコーダ→距離の換算は `2.8 cm`
- 比 0.9643 が，観測されたodo/encの食い違いと小数4桁まで一致

両方を `5.6f / 2.0f`（= 2.8cm）に統一して解決しました．
28.3mmも試しましたが行き過ぎで，独立した2回の走行から求めた実効半径は27.82〜28.00mmでした．

較正後の精度：**距離誤差 ±1〜1.5%，方位誤差 ±0.4°以内**．

## 5. カメラとオドメトリの突き合わせ

軸の向きを手で測ると，それ自体が誤差源になります．
そこで次の手順で数値的に揃えます．

1. **時刻オフセットの推定**：速度の相互相関が最大になるラグを探す
2. **剛体整合（Procrustes）**：回転のみ推定，スケールは1固定．鏡映が入っていないか行列式で確認する

この整合でカメラ軌跡をオドメトリの機体座標系へ変換すれば，前方成分・横成分の比較が
手測りなしで直接できます．整合後の形状残差は平均1.2cm程度でした．

### 運用の指針

- 普段の検証は**カメラを審判役**にして回す
- ときどきメジャー実測を行い，カメラ自体を疑う

### メジャー実測を正確にとる手順

1. スタート時に定規や板を両輪側面に当て，**車体を床板の継ぎ目と平行に置く**（初期向きの誤差を0.5°以下にできる）
2. 前方距離は板目に沿ってメジャーで測る
3. 横距離は板目からの垂直距離として測る．直角の出し方は，15cm折り紙を当て木にすると正確

この手順にするだけで，成分誤差は8cmから2cm以下に下がりました．

## 6. 出力ファイルが更新されないとき

Windowsで `軌跡画像.jpg` を画像ビューアで開いたまま再実行すると，ファイルがロックされて
上書きに失敗します．対策として次を入れています．

- 走行中も60フレーム（約2秒）ごとに軌跡画像を更新する
- 上書きに失敗したら `軌跡画像_143052.jpg` のように時刻付きの別名で保存し，例外で落ちない
- Ctrl-C で中断してもそこまでの結果を保存する
